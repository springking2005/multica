# 路线图审核 W1：当前状态描述核查

> 审核日期：2026-05-13
> 审核对象：`docs/后续开发路线图.md`
> 核查范围：按要求仅核对 `bodiagent/settings.py`、`daemon_cli/providers/__init__.py`、`frontend/templates/`

## 结论

路线图对模板数量、Django app 列表、基础设置中的 PostgreSQL 默认配置、Redis/Channels/Celery 基础配置、邮件默认 console backend、文件存储可通过环境变量切换等描述大体成立。

但当前状态描述中有几处会误导后续排期，主要集中在 Provider 检测能力和前端模板“可用 / CRUD”程度上。以下为发现的不准确项。

## 发现

### 1. “Gemini CLI 可检测”与实际 Provider 检测代码不符

路线图现状速览写道：

> daemon_cli ... 支持 Claude/Codex/OpenClaw 三大 Provider（Gemini CLI 可检测但 Provider 待实现）

实际代码中，`daemon_cli/providers/__init__.py` 只导入并导出 `ClaudeProvider`、`OpenClawProvider`、`CodexProvider`。`detect_providers()` 只检查 `claude`、`openclaw`、`codex` 三个可执行文件，`get_provider()` 也只接受这三个名称。

证据：

- `daemon_cli/providers/__init__.py:1` 文档字符串只列出 `claude, openclaw, codex`
- `daemon_cli/providers/__init__.py:16` `__all__` 不包含 Gemini
- `daemon_cli/providers/__init__.py:27-31` `executables` 不包含 `gemini`
- `daemon_cli/providers/__init__.py:41-47` `get_provider()` 不支持 `gemini`

建议修正文案：

> daemon_cli 支持 Claude/Codex/OpenClaw 三大 Provider；当前检测逻辑仅检测这三类 CLI，Gemini Provider 和 Gemini CLI 检测均未实现。

### 2. “基础 CRUD 页面可用”对 Agent 页面描述过度

路线图 P0.1 写道：

> 基础 CRUD 页面（Dashboard / Issues 看板+详情 / Agents 列表 / Inbox 列表 / 设置）可用

但 `frontend/templates/agents/list.html` 不是完整 CRUD 页面。它包含 Agent 列表加载和创建弹窗，但没有编辑、删除、归档、详情或配置入口。路线图后续又把“Agent 配置/编辑页”列为待补全，这一部分是正确的；问题在于“基础 CRUD 页面可用”的总括描述过强。

证据：

- `frontend/templates/agents/list.html:23-27` 仅通过 `GET /api/agents/` 加载列表
- `frontend/templates/agents/list.html:52-55` 仅通过 `POST /api/agents/` 创建 Agent
- `frontend/templates/agents/list.html:123-147` 渲染卡片，但没有编辑/删除操作

建议修正文案：

> Agents 列表和创建弹窗已存在；编辑、删除、配置、关联 skills/daemon 尚无前端界面。

### 3. Issue 详情页“可用”表述偏乐观

Issue 详情模板存在，但它把多个 JSON API 响应直接 `hx-swap="innerHTML"` 到 HTML 容器中，没有像看板、Agents、Inbox 页面那样把 API JSON 解析为 HTML。

这意味着如果 `/api/issues/{id}/`、`/api/issues/{id}/comments/`、`/api/activity/` 返回的是 DRF JSON，而不是 HTML partial，页面会直接显示 JSON 字符串或非预期内容，不能严格称为“详情页可用”。

证据：

- `frontend/templates/issues/detail.html:10-14` 直接把 `/api/issues/{{ issue_id }}/` 响应替换进详情卡片
- `frontend/templates/issues/detail.html:26-30` 直接把 comments API 响应替换进评论列表
- `frontend/templates/issues/detail.html:58-62` 直接把 activity API 响应替换进活动时间线
- 同文件没有对应的 `htmx:afterSettle` JSON 解析脚本

建议修正文案：

> Issues 看板可渲染 API 数据；详情页骨架已存在，但仍需 HTML partial 或前端 JSON 渲染逻辑才能稳定可用。

### 4. Issue 看板存在，但“拖拽卡片以更改状态”尚未实现

看板模板顶部文案写着“拖拽卡片以更改状态”，路线图 P2.2 又把“Issues 看板拖拽”列为投产后迭代。实际模板只有按状态加载卡片和渲染列表的逻辑，没有拖拽事件、drop zone、排序或状态更新请求。

证据：

- `frontend/templates/issues/board.html:9-10` UI 文案宣称可拖拽
- `frontend/templates/issues/board.html:39-143` 各列只配置 `hx-get`
- `frontend/templates/issues/board.html:151-194` 脚本只解析 JSON 并渲染卡片/数量
- 未见 `dragstart`、`dragover`、`drop` 或状态更新请求

建议修正文案：

> Issues 看板列表渲染可用；拖拽改状态尚未实现，仍属于 P2.2 待办。

### 5. 设置页“个人设置可用”应限定为个人资料表单，偏好/通知未持久化

设置页包含个人资料表单、语言选择、主题切换和通知偏好展示。但只有个人资料表单绑定了 `hx-patch="/api/me/"`；语言选择和通知复选框没有 name、form、HTMX 请求或保存逻辑。主题只写入浏览器 `localStorage`。

证据：

- `frontend/templates/settings/profile.html:13-16` 个人资料表单会 PATCH `/api/me/`
- `frontend/templates/settings/profile.html:51-55` 语言选择没有提交逻辑
- `frontend/templates/settings/profile.html:62-79` 主题只通过 `localStorage` 保存
- `frontend/templates/settings/profile.html:90-117` 通知复选框没有提交逻辑

建议修正文案：

> 个人资料编辑基础表单已存在；语言、主题、通知偏好仍主要是静态/本地 UI，未形成完整后端持久化设置页。

### 6. 前端“可用”应区分页面骨架、JSON 渲染和完整交互

路线图的“前端基础模板可用”和“基础 CRUD 页面可用”容易让读者理解为这些页面已经能完成主要业务闭环。实际情况更接近：

- 模板数量确为 15 个；
- 登录、注册、Dashboard、Issues 看板、Agents 列表、Inbox、个人设置等入口存在；
- Dashboard / Issues 看板 / Agents / Inbox 主要依赖 HTMX 请求 JSON API，并在部分页面用前端脚本把 JSON 转为 HTML；
- Issue 详情、设置偏好、通知偏好、Agent 编辑/删除等仍未达到完整可用或 CRUD 闭环。

证据：

- `frontend/templates/` 当前共有 15 个 HTML 文件
- `frontend/templates/issues/board.html:151-194`、`agents/list.html:114-157`、`inbox/list.html` 中存在 JSON 渲染脚本
- `frontend/templates/issues/detail.html` 缺少等价 JSON 渲染脚本

建议将当前状态改为：

> 前端 15 个模板已搭建，基础导航和部分列表页可通过 HTMX + JSON 渲染展示数据；多个页面仍是骨架或半成品，尚未形成完整 CRUD/交互闭环。

## 已核实为基本准确的描述

- `settings.py` 默认数据库 ENGINE 为 PostgreSQL。
- `settings.py` 中 Channels 使用 Redis channel layer，Celery broker/result backend 也指向 `REDIS_URL`。
- `settings.py` 默认邮件 backend 为 `django.core.mail.backends.console.EmailBackend`。
- `settings.py` 的 `STORAGES["default"]["BACKEND"]` 可通过 `DJANGO_STORAGE_BACKEND` 环境变量切换，默认本地 `FileSystemStorage`。
- `frontend/templates/` 下确有 15 个 HTML 模板。

## 范围说明

本轮未核查路线图中关于测试数量、API 路由数量、Docker 构建、ASGI WebSocket 路由、`settings_prod.py`、CI/CD、schema/openapi 合约验证的真实性，因为用户指定的核查文件不包含这些实现面。上述项目不应由本报告视为已确认。
