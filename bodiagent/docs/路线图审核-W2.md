# 路线图优先级审核 - W2

**审核对象**：`bodiagent/docs/后续开发路线图.md`  
**审核日期**：2026-05-13  
**审核范围**：仅审核优先级分层、前置依赖和建议时间线，不审核事实描述完整性。

## 结论

路线图把「核心前端、daemon 端到端、Docker/PG/生产配置」列为 P0 的方向基本正确，但当前优先级存在 4 个需要调整的点：

1. WebSocket 路由未注册是 Chat UI 的硬前置，应从 P0.1 中拆出来并排到 P0.1 之前。
2. PostgreSQL 迁移验证不应依赖 P0.3 Docker 完成；应和 Docker 并行，且排在大部分前端 CRUD 验收之前。
3. CI/CD 的「从零建设」描述已过期，优先级应改成「补齐构建/发布门禁」，而不是完整 P1.1。
4. 安全加固、日志监控、健康检查不宜全部放在 P1 后段；最小生产可观测性应进入 P0.5。

## 推荐新的 P0 执行顺序

1. **P0.0 WebSocket 最小打通**：注册 ChatConsumer 路由，补一个连接/发送 smoke test，确认 `/ws/chat/{session_id}` 或实际约定路径可用。
2. **P0.1 PostgreSQL 基线**：在 pgvector/pg17 上跑 migrate、核心测试、合约校验，记录与 SQLite 差异。
3. **P0.2 Docker compose 基线**：Web + PostgreSQL + Redis 可启动，`/health/` 返回 200，collectstatic 不依赖缺失环境变量。
4. **P0.3 daemon_cli 真实链路**：至少一个真实 AI CLI 完成领取任务、执行、回传结果；并覆盖取消、崩溃、断线恢复中至少一个失败路径。
5. **P0.4 核心前端补齐**：先做 Token/Agent/Chat，再做 Project/Autopilot；移动端验收保留。
6. **P0.5 最小生产配置**：SMTP/Sentry/Redis、JSON 日志、Nginx WebSocket 升级模板、`check --deploy` 结果归档。

## 优先级风险

- **Chat UI 被放在 P0.1 但 WebSocket 未先注册**：这会导致前端工作先写大量降级或轮询逻辑，之后再返工接 WebSocket。
- **CI 描述与仓库现状不一致**：已有 BodiAgent CI 工作流包含 ruff、mypy、pytest、PG service 和 contract validation；路线图若继续按「无 CI」排期，会高估 P1.1 并低估 build/release 工作。
- **生产配置拆得过散**：P0.5、P1.5、P1.6 目前互相重叠。投产前至少需要健康检查、结构化日志、Sentry 验证和 deploy check 同时闭环。
- **P0.1 工作量可能被低估**：Chat、Autopilot 配置、Agent 编辑都不是普通 CRUD；若保持 Django Templates + HTMX，建议把 Chat 和 Autopilot 分成独立验收，不要合并成一个前端模板大包。

## 可保留不变的优先级

- P2.1 OAuth、P2.4 i18n、P3 企业认证/扩缩容等放在投产后或远期合理。
- P0.2 daemon_cli 端到端作为投产阻塞项合理，因为产品核心价值依赖真实 agent 执行链路。
- P0.3 Docker 验证作为投产阻塞项合理，但建议与 PG 验证并行，而不是作为 PG 的前置。

## 最小修改建议

如果不想大幅重排路线图，建议至少做三处文本修改：

1. 在 P0 最前新增「P0.0 WebSocket 路由注册与 smoke test」。
2. 将 P0.4 的前置依赖从「P0.3」改为「可使用本地或 CI PostgreSQL 服务」，并把它排到 P0.3 前。
3. 将 P1.1 现状从「无任何 CI 配置」改为「已有 BodiAgent CI 基线，缺 build/release/coverage/分支保护验证」。
